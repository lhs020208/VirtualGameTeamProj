## 기록 내구성: 실제 UE와 모의 테스트 구분
`UE_ReportLock_220707/INTEGRATION_RESULT.json`의 실제 Unreal PIE 검사에서 Windows CreateFileW 핸들을 FILE_SHARE_DELETE 없이 열어 실제 status.json 교체를 막았다. 약 21.97초의 별도 실행, 동일 20,000입자 설정이다.

- 잠금 중 물리 시간이 0.079039998→0.191679995 s로 진행했고 11개 고유 recovery JSON이 남았다.
- 잠금 해제 후 0.242079994 s 상태가 정상 status.json에 게시됐다.
- 종료 상태 게시 중 다시 잠그자 최종 recovery를 선택했고, 해제 후 정상 최종본으로 복귀했다.

이는 실제 OS 공유 잠금이며 예외를 흉내 낸 테스트와 다르다. 별도의 `REPORT_IO_MOCK_REGRESSION.json`은 연속 실패·UUID 파일 고유성·백업 쓰기 실패를 확인한다. 실제 UE 검사는 공유 최신 보고서 판독기를 검증했으며, 모든 디스크 고장이나 전체 장기 보고서 렌더러의 모든 경우를 보장하지 않는다. 기본 파일 게시 실패 시 불변 recovery를 쓰고 물리를 계속하며, 판독기는 revision이 가장 높은 완전한 JSON을 선택한다.

### 법선 정밀도 근거
`NORMAL_QUANTIZATION_EVIDENCE.json`: 위치 보정이 float32 세계 좌표의 몇 ULP에 불과한데, `granular_plant_cl.inc`의 normalize(p-initial)가 이 작은 차이를 접촉 법선으로 사용한다. B 대표는 실제 접촉 방향과81.59도, WH 대표는18.43도 차이가 난다. WH에서는 실제 약37.3도 경사 대신 약19.5도처럼 처리되어 μ=0.4의 정지/미끄럼 판정을 바꿀 가능성이 있다. 이는 강한 원인 근거지만 수정 효과는 아직 검증하지 않았다. 삼각형 가장자리에서는 면 법선과 접촉 방향이 원래 다를 수 있으므로, 면 법선 차이만으로 오류라고 판정하지 않았다.

## 정확한 체크포인트/재개: 현재 경로에서 미지원
현재 GPU plant 경로의 set_state는 위치·속도를 받지만 시간과 회전각을0으로 초기화하고 캐시/일부 누적 상태를 지운다. UE ExportSnapshot CSV에는 위치와 ID/종류/시간만 있고 속도가 없다. 다른 ClumpWorker의 checkpoint는 이 경로에 적용되는 기능이 아니다. 종료된 원 실행을 위치 CSV만으로 정확히 이어갈 수 없다.

정확한 재개에는 완료된 GPU 스텝 경계에서 위치·속도·ID/종류, 물리시간/스텝, 회전각/RPM, 동일 형상/설정/물성 해시, 요청/적용 압력과 밸브, 제어 단계·대기 명령·코호트/타이머가 필요하다. 유지되는 내부 상태는 저장하거나 재구성 동등성을 검증해야 한다. 현재 비활성 회전/접촉 이력 기능을 활성 상태처럼 요구하지는 않지만, 향후 활성화하면 해당 각속도/접촉 이력도 범위에 포함해야 한다. 현재 준정상1D 공기는 동일 버전·적용 경계조건으로 재구성 가능성을 검증해야 한다. 연속 실행 대 저장/복원 실행의 짧은 동등성 검사가 선행되어야 한다.

## 다음 최소 작업 제안 — 이번 단계에서는 미실행
1. 접촉 법선이 미세한 세계 좌표 차이에 의존하지 않도록 실제 기하 법선을 전달하는 수정부터 한다. B/WH 단독 재현, 경사면, 다중 접촉, 회전벽, 캐시 재사용 회귀 검사를 먼저 수행한다. 허위 정체 개선이 기대되지만 해소율/성능 향상률은 아직 약속할 수 없다. 다중 접촉 법선 결합 오류가 주요 위험이다.
2. BV272 턱과44→25mm 연결의 의도된 내경을 정한 뒤 별도 시험용 형상에서 수정한다. 통로만 정합시키고 실제 부품을 삭제해 성공을 만들지 않는다. 형상·유량·충돌 일치 검사가 필요하다.
3. 정확한 체크포인트를 별도 작업으로 구현하고 짧은 동등성 검사를 통과시킨다. 저장 파일 버전과 비동기 스텝 일관성이 위험 요소다.
4. 위 짧은 검사 뒤에만 전체 이송과 실제12초 회전을 다시 검증한다. 기존 실측 속도에서 동일 절차 재시험은 조건부 약3.5시간이다. 변경 효과가 확인되기 전 같은 장기시험을 반복할 이유는 없다. 구현 소요시간은 아직 실측하지 않았으며 각 항목을 한 작업 단위로 나누는 편이 적절하다.
