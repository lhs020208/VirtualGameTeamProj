# 추가 최적화 06 — 전송·표시 버퍼 재사용 및 비동기 읽기

## 구현과 유지 조건

`-GrainStream` 선택 옵션을 추가했다. 물리 시간 간격, 반복 수, 입자 수, 접촉식, 중력·마찰과 저장된 레벨은 유지한다. 화면 밖 입자도 모두 계산·전송한다. 표시를 위한 보간·외삽이나 녹화 재생은 사용하지 않는다.

- OpenCL 비차단 읽기 요청과 완료 확인 API를 분리했다. 전송 중인 호스트 메모리는 완료 전까지 수정하거나 해제하지 않는다.
- 한 번에 하나의 읽기만 허용하고 중복 요청을 거부한다. 동일한 in-order 큐가 읽기 요청 시점의 위치를 다음 물리 계산보다 먼저 읽도록 보장한다. 별도 전송 큐나 GPU 계산/전송 중첩을 구현했다고 주장하지 않는다.
- 완료 전에는 이전의 완전한 표시 상태를 유지하며 물리 계산은 계속할 수 있다. 대기열이 무제한 쌓이지 않는다.
- 요청 시점의 시뮬레이션 시각, 회전각, 경과 시간, 게이트 상태를 함께 보관한다. 완료된 위치와 해당 메타데이터를 한 잠금 안에서 게시해 입자와 날개 시점이 섞이지 않는다.
- 읽기용/작업용/게시용 벡터의 저장 공간을 swap하여 재사용한다. 게임 스레드 복사 벡터와 변환 배열도 재사용한다. 안정된 입자 수에서는 매번 새 대형 배열을 만드는 경로를 줄인다.
- 초기 위치의 중복 GPU 읽기를 제거했다. 기존 약 20Hz 표시 요청 정책은 유지하며, 물리 배치 또는 전송 완료가 늦으면 그보다 낮아질 수 있다.
- Pause 중에도 완료를 확인한다. 종료 시 진행 중 읽기를 완료하고, Reset/파괴 시 DMA 완료를 기다린 뒤 이벤트와 메모리를 정리한다. 새 세대에 이전 읽기 결과가 섞이지 않는다.

여전히 게임 스레드로의 위치 복사와 ISM 전송, 생성기 내부 변환 복사, 통계/파일 기록은 남아 있다. 이번 작업은 완전한 GPU 직접 렌더링 전환이 아니다. 기본 ON 결정은 작업 08에서 한다.

## 계측과 재현

`worker_timing.json`의 `stream_enabled`와 `readbacks`로 경로 및 주기적 읽기 요청 수를 확인한다(초기 읽기 제외). `snapshot_wall_s`는 CPU 읽기 요청/완료 확인에 소비한 시간이며, 비동기 요청 이후 대기한 벽시계 시간 전체를 의미하지 않는다. GPU 이벤트를 켠 경우 완료된 읽기의 GPU 시간은 기존 `snapshot_readback_gpu_s`에 기록한다.

에디터 종료 후:

```powershell
python -B Scripts/run_additional_optimization06.py --run
python -B Scripts/run_additional_optimization06.py --run --modes stream --seconds 30 --repeats 1 --label extended30
```

양쪽 모두 이웃 안전 재사용을 켜고 경계 후보 축소는 끈다. 12초 × 경로별 2회, 두 번째 반복 역순, GPU 이벤트 계측 OFF. 초기 SHA/수량/그룹/질량과 마지막 기록의 겹침·벽/날개 침투를 검사한다.

## 검증 한계

소규모 시험은 읽기 요청 이후 물리 계산을 진행해도 요청 시점의 위치가 반환되는지, 비동기 읽기를 끼운 물리 결과가 읽기 없는 결과와 같은지 확인한다. 중복 요청, 반복 버퍼 재사용, 비차단 완료 확인, Reset, pending 상태 파괴, 프로파일링 ON/OFF를 검사한다.

대규모 기하 검사는 마지막 저장 위치에 대한 검사다. 모든 중간 시점 또는 실제 분체 물성 정확도를 인증하지 않는다. 표시 상태는 계산보다 늦을 수 있으며 시뮬레이션 시각을 그대로 표시한다.

## 12초 비교 결과 (2026-10-27)

RTX 4060 Ti, 초기 5만 입자, 두 경로 각 2회:

| 항목 | 기존 동기 읽기 | 비동기 읽기·배열 재사용 |
|---|---:|---:|
| 전체 배속 중앙값 | 0.279849 | 0.280071 |
| 읽기 CPU 시간/요청 중앙값 | 0.1845ms | 0.1328ms |
| 표시 복사·잠금 CPU 시간/갱신 중앙값 | 0.0620ms | 0.0598ms |
| 변환 생성 CPU 시간/갱신 중앙값 | 0.3212ms | 0.3134ms |

읽기 CPU 비용은 약 28% 감소했지만 전체 처리속도 차이는 약 0.08%로 유의한 성능 이득으로 판단하지 않는다. 새 읽기 시간은 비차단 요청/완료 확인 CPU 비용이며 전체 전송 지연과는 다르다. 이 장면의 주 병목이 전송·표시라고 볼 근거는 없다. 기본 OFF를 유지하고 작업 08에서 조합/기본값을 결정한다.

네 실행 모두 고정 초기 SHA, 수량·그룹·질량·유한값 및 최종 기록의 겹침/벽·날개 침투 검사를 통과했다. [원본 비교 결과](comparison/measurement.json).
