# 최적화 06 완료 — 계산 스레드와 Unreal 표시 분리

2026-10-22 / `PowderSimulationOptimization`

## 구현

- `ClumpWorker`가 전용 C++ 스레드에서 ClumpWorld·접촉 이력·프로파일·혼합 측정을 소유한다. Unreal 객체를 계산 스레드에서 접근하지 않는다. 고정 dt, 재료, 충돌식은 유지한다.
- 실행 중 기본 30Hz(1~120Hz 조절)의 불변 스냅샷만 게시한다. 최신 한 개를 보관하는 mailbox이며 큐가 쌓이지 않는다. UI는 새 스냅샷만 반영한다. 전체 solver/history 복사는 명시적인 정지 상태 export에서만 한다.
- 시작·정지·한 단계·reset 명령은 직렬화한다. 정지/한 단계는 진행 중인 단계가 끝날 때까지 기다리는 barrier다. reset은 이전 worker를 join하고 새 세대를 만든다. EndPlay/소멸 시 join한다. 세대·순번·단계 역행 스냅샷은 표시에서 거절한다. 수치 오류는 마지막 승인 상태에서 정지하고 오류를 게시한다.
- 물리 실행은 화면 Tick/DeltaSeconds와 무관하다. `bRealtimePacing`은 worker 자체의 monotonic clock으로 목표 속도를 제한한다. dt 확대나 시간 건너뛰기는 없다. 꺼두면 처리 가능한 속도로 계속 계산한다.
- 동일 인스턴스 수에서는 `BatchUpdateInstancesTransforms`로 일괄 갱신한다. 개수가 바뀔 때만 재구성한다. `MaxDisplayedPebbles`의 일정 간격 표시 LOD는 계산·측정·내보내기 입자 수에 영향을 주지 않는다.
- 혼합 측정은 기존 물리 시간 간격(`MixingSampleSeconds`)으로 수집한다. 화면은 마지막 측정값과 측정 시각을 보여준다. 매 프레임 별도 재측정하지 않는다.

## 조작 및 설정

- Space: 실행/정지, N: 정확히 한 단계, R: 초기화, O: 정지 상태 내보내기. 기존 카메라 조작 유지.
- `Clump > Display > Display Snapshot Hz`: 기본 30. 초기화 또는 정지 후 실행 시 적용.
- `Max Displayed Pebbles`: 기본 1024. 0은 입자 표시만 숨긴다. 변경 후 초기화하면 즉시 반영된다. HUD는 표시 수와 실제 구성 구 수를 구분한다.
- 기존 저장 속성 `StepsPerFrame`은 호환성을 위해 이름을 보존하되 UI 이름은 `Worker Batch Steps`다. 이제 화면당 단계 수가 아니라 worker의 배치 크기다. `ComputeBudgetMs` 역시 worker 배치 예산이며 프레임 정지 시간이 아니다. 명령은 매 단계 경계에서 확인한다.
- 재료·형상·dt·측정 설정 변경은 초기화 후 적용. 출력의 `performance.csv`에는 물리 단계별 계측, worker 계산, snapshot 복사, display sync CPU 시간을 구분한다. worker 시간은 물리 계측 시간을 포함하므로 서로 더하면 안 된다.

## 검증

- Core 전체 26/26 통과. 최종 오류 상태 및 표시 생략 개선 후 worker 전체 검사를 재실행하고, 재현 runner로 한 번 더 통과.
- 최종 Unreal 빌드 성공, 자동 검사 14/14 통과(경고 0, 실패 0).
- 32몸체 12,000단계(0.024 물리초), snapshot 1/30/120Hz × 3회. 소비 주기 50/16/1ms 및 프로파일 on/off에서 직접 계산과 bodies CSV·혼합 파일이 byte-identical. 접촉 이력 수와 checkpoint 후 다음 단계도 동일.
- 정지 뒤 시간 불변, 한 단계 정확성, 화면 Tick 없이 진행, 독립 pacing, pause 시간 제외, 동시 명령/reset, 오래된 불변 snapshot, 세대 전환, 실행 중 소멸, 잘못된 설정, 계산 중 안전 검사 실패 후 상태 보존·재초기화 검사 통과.
- Unreal에서 8개 표시와 0개 표시 모두 32개 실제 계산. 서로 다른 Tick delta에서도 2,000단계 후 위치·CSV 동일, 측정 샘플 11개. 같은 snapshot의 반복 Tick은 추가 인스턴스 갱신을 하지 않는다.

## 비용 측정 및 해석

최종 NullRHI 시험: 32몸체 × 2,000단계, 표시 8개:

| 항목 | CPU 시간 |
|---|---:|
| worker 계산 | 0.095675 s |
| snapshot 복사 | 0.000007 s |
| 표시 갱신 5회 | 0.000264104 s |
| 표시 0개일 때 표시 갱신 5회 | 0.0000290982 s |

두 worker를 함께 실행한 기능 검사이므로 위 값으로 솔버 속도 향상 배율을 주장하지 않는다. NullRHI는 인스턴스 갱신 CPU만 포함하며 GPU 렌더링/FPS 측정은 아니다. 별도의 32입자 Unreal pacing 시험은 약 0.03628배속이었다.

독립 Core runner의 직접 계산은 약 0.3988초, worker 관측 완료는 약 0.4171~0.4386초였다. worker의 동기화·계측·관측 대기 비용이 있으므로 06 자체를 물리 솔버 가속으로 평가하지 않는다. 목적은 UI에서 물리 계산을 분리하고 표시 비용을 제한하는 것이다.

## 제한과 다음 작업

300몸체/1024구 한도를 그대로 유지한다. GPU 계산·접촉 병렬화·완전한 SoA 전환은 하지 않았다. mm·kg 대량 조건의 0.1배속 목표는 미달이며 실제 원료 검증도 별도다. 단일 단계가 오래 걸리면 pause/reset은 그 단계 완료까지 기다린다. 표시 LOD는 거리별 LOD가 아닌 안정적인 인덱스 간격 샘플링이다. 스냅샷이 최신 물리 상태보다 약간 늦게 표시되는 것은 의도된 동작이다.

다음은 계획의 최적화 07이다. 커밋·푸시는 수행하지 않았다.
