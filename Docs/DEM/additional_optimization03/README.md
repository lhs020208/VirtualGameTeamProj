# 추가 최적화 03 — GPU 이웃 후보 목록 구축

## 구현 범위

입자마다 접촉 가능성이 있는 이웃 ID를 GPU 목록으로 구성하고, 접촉 커널이 이 목록을 순회하는 선택적 경로를 추가했다.
현재는 **모든 위치 보정 반복 직전에 격자와 후보 목록을 재구축**한다. 이전 반복/시간 단계의 목록은 재사용하지 않는다. 위치 보정이나 경계 투영으로 다음 반복에 새 접촉이 생겨도 현재 좌표로 다시 찾는다.
작업 04에서 이동량과 위치 보정량을 감시하는 안전 재사용을 구현할 예정이다. 이번 단계 자체로 속도 향상을 약속하지 않는다.

- 기존 27개 인접 셀 탐색에서 자기 자신을 제외한 후보를 모은다.
- 거리 필터는 `(2r)^2 × 1.00001`로 소폭 바깥 여유를 두고, 실제 접촉 커널은 기존의 엄격한 `거리² < (2r)^2`를 다시 검사한다. 물리 반지름이 커지는 것은 아니다. 이 작은 수치 여유를 목록 재사용을 위한 이동 여유로 사용하지 않는다.
- 기존 접촉 법선·마찰·보정량 제한·경계 투영·속도 계산을 유지한다.
- 목록은 입자별 고정 용량(기본 64개, 허용 1–256개)이다. 초과한 입자는 **잘린 목록을 쓰지 않고 해당 반복에서 기존 전체 격자 탐색**을 수행한다.
- 기존 격자 탐색 순서대로 목록을 저장한다. 병렬 격자 삽입 순서와 컴파일 경로 때문에 장시간 입자별 비트 일치까지 보장하지는 않는다.
- 저장 공간 할당 실패는 명시적 오류로 처리한다. 5만 개·64칸에서는 추가 GPU 버퍼가 약 13.0MB다.

기본 실행은 기존 경로를 유지한다. 레벨/생성기/데이터 에셋/물리 설정을 수정하지 않았다.

## 실행 및 기록

- 언리얼 실행 인수 `-GrainCandidates`: 후보 목록 경로 활성화.
- `-GrainCandidateCapacity=64`: 저장 칸 수 지정. 범위를 벗어나면 실행을 거부한다.
- `-GrainProfile`, `-GrainProfileSplit`과 함께 사용할 수 있다.
- `granular_run`의 기존 인수 뒤에 `candidates candidate_capacity`를 추가했다.
- 비교 실행: 에디터를 종료한 후 `python -B Scripts/run_additional_optimization03.py --run`.
  기본은 기존/후보 각각 12초 시뮬레이션 2회이며, 두 번째 반복은 역순으로 실행한다.

`timing.json` schema 3에 추가한 항목:

| 항목 | 의미 |
|---|---|
| candidates_enabled | 후보 경로 활성화 여부 |
| candidate_capacity | 입자당 저장 칸 수 (OFF일 때 0) |
| candidate_builds | 목록 재구축 횟수; GPU 계측 OFF에서도 기록 |
| candidate_fallback_particle_iterations | 용량 초과로 전체 탐색한 입자×반복 횟수 |
| candidate_build_gpu_s / candidate_build_calls | 계측 ON에서 후보 구축 커널 시간/실행 수 |

초과 횟수는 두 개의 32비트 atomic 카운터로 합산해 64비트로 읽는다. 목록 구축은 기본 접촉과 별도 커널이므로 재사용 전에는 추가 탐색·메모리·커널 실행 비용이 생긴다.

## 검증 방법

새 `optimization_granular_candidates` 시험:

- 고정 난수 장면 16개(일반/MX301, 격자 범위 모드 조합)를 CPU 모든 쌍 기준과 대조.
- 격자 경계·양/음 좌표·맞닿는 입자·서로 떨어진 벽 근처 입자 검사.
- 같은 위치의 70개 입자로 기본 64칸 초과를 유발하고 전체 탐색의 모든 접촉 포함 확인.
- 1칸 용량을 강제로 넘긴 경우 기존 GPU 전체 탐색과 결과 비교.
- 독립적인 CPU O(N²) Jacobi 접촉 계산과 GPU 기존/후보 경로를 각각 비교(허용 위치 차이 2μm).
- 첫 위치 보정 후 새 접촉이 생기는 세 입자 사례를 CPU 기준과 비교.
- 벽 충돌 궤적, 분리 진단과의 조합, Reset, 잘못된 용량 거부 검사.

`inspect_candidates()`는 4,096개 이하의 진단용 읽기 API다. 현 좌표에서 GPU 목록을 만들고 읽는다. 용량 초과 행은 GPU의 격자 head/link를 읽어 기존 순회 후보를 복원한다. 생산 경로에서 호출하지 않으며, 이 검사가 독립적으로 기존 공간 격자 자체의 모든 경우를 증명하는 것은 아니다. 실제 fallback 접촉 계산은 별도의 궤적 비교로 확인한다.

현재 소규모 시험에서 총 **8,690개 방향 있는 CPU 접촉 쌍**에 대해 누락이 없었다. 기존 `optimization_granular_gpu` 시험도 통과했다.

5만 개 비교에서는 초기 SHA, 입자 수/그룹/질량/유한값 및 최종 겹침·벽·날개 침투를 검사한다. 최종 스냅샷 검사는 모든 중간 시각이나 실제 분말 정확도를 인증하지 않는다.
## 2026-10-27 실측 결과

동일 장면/물리 설정(5만 개, 64.8kg, dt=0.000375s, 반복 16회, 배치 32), 각 경로 12초 시뮬레이션 2회, GPU 이벤트 계측 OFF, 1280×720 및 최대 30fps.

| 경로 | 배속 범위 | 중앙값 |
|---|---:|---:|
| 기존 전체 격자 탐색 | 0.20095–0.20250 | 0.20173 |
| 매 반복 후보 목록 재구축 | 0.16898–0.16977 | 0.16938 |

두 중앙값의 역비로 계산한 소요시간 증가는 약 **19.1%**다. 표본은 각 2회이며 통계적 확정값이 아니다. 예상대로 재구축 비용이 추가되었으므로 **후보 경로는 기본 OFF**로 유지한다. 작업 04에서 안전 재사용으로 재구축 횟수를 줄인 뒤 다시 성능과 접촉 누락을 검증해야 한다.

- 4회 모두 초기 상태 SHA 동일, 입자 수 50,000개, 각 그룹 25,000개, 질량 64.8kg, 유한값 검사를 통과했다.
- 최종 겹침/반지름 최대 0.05991 (기준 ≤0.1).
- 최종 벽 침투 최대 약 4.80e-8m, 날개 침투 최대 약 4.02e-8m (기준 각각 ≤0.0001m).
- 후보 경로의 목록 구축 횟수 512,992회/512,912회. 각각 실제 물리 시간 단계 수×16회와 일치했다.
- 5만 개 실행의 용량 초과 fallback은 0회. fallback 동작 자체는 강제 초과 단위 시험으로 검증했다.
- 마지막 기록 시각은 실행별로 약 11.94–12.02초로 다르다. 최종 혼합 지표나 입자별 좌표가 같은 시각에 정확히 일치한다고 주장하지 않는다.
