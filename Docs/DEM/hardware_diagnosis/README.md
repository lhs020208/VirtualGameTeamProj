# CPU·GPU 실행 병목 진단 — 현재 5만 개 입자

2026-10-28. 기준 커밋 `80b1292`, RTX 4060 Ti 16GB / i7-14700KF (20코어, 28논리 프로세서).

## 결론

현재 가장 크게 확인된 비용은 **물리 계산과 화면 렌더링의 GPU 자원 경쟁**이다. CPU 스레드 수를 늘리기보다 화면 FPS 예산을 먼저 제한하는 것이 유효했다. 다만 GPU 사용률 97%가 연산 유닛·메모리 대역폭을 이론적 최대까지 사용한다는 뜻은 아니다. 커널 내부 최적화 여지는 남는다.

0.1배속 계산 전용 시험의 GPU 사용률 중앙값은 31%, 제한 없는 12초 계산은 96~98%였다. 속도 제한 상태에서 보이는 낮은 사용률을 최대 처리 성능의 증거로 삼으면 안 된다.

## 변경한 진단 기능

- `GranularTiming` schema 6: 물리 작업 스레드의 실제 OS CPU 시간, 제출 구간 CPU 시간, GPU 이벤트 구간 길이와 명령 사이 간격 추가.
- `diagnostic_local_size`: 64/128/256 GPU workgroup 비교. 기본값 128 유지, 접촉식·dt·반복 수 변경 없음.
- CMake `granular_diagnose`: 저장된 초기 위치·성분을 이용하는 현재 가상 A/B 전용 계산 실행기. 범용 프리셋 로더는 아니다.
- 배치 크기, 표시용 readback 주기, 상세 계측 유무, 속도 제한을 분리한 실행/모니터/감사/보고 스크립트 추가.
- 작은 CPU 기준 문제로 세 workgroup의 접촉 결과와 GPU 시간 분해를 검사하는 회귀 시험 추가.
- 실행 스크립트는 75°C 또는 155W 이상, 계측 실패 시 자신이 시작한 시험 프로세스를 중단한다. 이는 이번 시험의 보수적 중단 기준이며 하드웨어 손상 한계라는 뜻은 아니다. 오버클럭·전력 제한을 변경하지 않았다.

실행 중인 에디터의 DLL은 교체하지 않았다. 새 진단 코어는 CMake Release로 빌드·검사했다. UE 비교는 기존 커밋된 구현에 명령행 옵션만 바꿔 수행했다. 기존 레벨, 에셋, 목표 0.1배속, 기본 workgroup은 유지했다.

## 동일 입자 조건

- 50,000개: 빨강 8,403 / 파랑 41,597, 총 약 40.838kg.
- dt 0.000375초, 접촉 16회, 30RPM, 회전 및 구름 저항 사용, 후보 재사용과 커널 최적화 사용.
- 모든 실행의 초기 위치는 동일 SHA256: `9547042760b376c83d3820068abe4e52b4093235062f4476a97c3fbb1cb8e29d`.
- 계산 전용 비교는 2,672번째 step에서 회전을 시작하도록 고정했다. UE는 기존 작업 스레드의 배치·스케줄링에 따라 1초를 넘긴 배치에서 시작하므로 프레임 단위로 동일한 궤적을 재생하는 비교는 아니다.
- 기존 에디터를 종료하지 않고 배경에 둔 비교다. 전체 GPU 계측에는 에디터 및 다른 앱의 부하가 포함된다. 코드상 GPU 이벤트 시간만 해당 OpenCL 큐의 측정값이다.

## 실측 성능

단위: 실제 1초당 진행한 시뮬레이션 초. 시작/컴파일 시간은 solver rate에 포함하지 않는다. GPU/CPU 모니터 통계는 프로세스 시작·종료 구간을 포함한다.

| 실행 | 물리 시간 | 속도 | 전체 GPU 사용률 중앙값 |
|---|---:|---:|---:|
| UE 기본 표시, 1280×720 | 12초 | 0.135743 | 97% |
| UE 화면만 30FPS 제한 | 12초 | 0.249261 | 98% |
| UE NullRHI, 렌더링 비활성 | 12초 | 0.323049 | 99% |
| 계산 전용 기본, 반복 1 | 12초 | 0.307196 | 97% |
| 계산 전용 기본, 반복 2 | 12초 | 0.308070 | 97% |
| 계산 전용 배치 32→128 | 12초 | 0.313950 | 98% |
| 계산 전용 workgroup 128→256 | 12초 | 0.324090 | 96% |
| 계산 전용 목표 0.1배속 | 약 4초 | 0.099941 | 31% |

UE 화면을 30FPS로 제한하면 이번 한 차례 12초 비교에서 약 **1.84배**, 렌더링을 끄면 약 **2.38배** 처리량이었다. NullRHI는 표시가 없어 사용자의 최종 사용 방식에 해당하지 않으며, 비용을 분리하기 위한 실험이다. 30FPS 제한은 실시간 계산·입자 표시를 유지하면서 사용할 수 있는 후보다.

현재 상태에서 관측된 수치이며 장시간·다른 입도·다른 장비의 최소 보장 속도가 아니다. UE 모드별 반복 시험과 장시간 관찰은 아직 하지 않았다. 목표 속도를 자동으로 높이지 않았다.

## CPU와 GPU에서 확인된 내용

계산 전용 기본 12초 실행은 벽시계 약 39초 중 작업 스레드의 실제 CPU 시간이 약 24.4~25.8초였다(평균 약 0.63~0.66 논리 코어). 배치 128은 CPU 시간을 약 18.3초로 줄였지만 속도 증가는 약 2%였다. CPU 제출 비용을 줄일 수는 있지만 이를 없앤 비율만큼 전체 계산이 빨라지지는 않는다. CPU와 GPU 작업이 겹치며, OS CPU 시간에는 드라이버의 실행·busy wait도 포함된다.

UE 프로세스 전체의 평균 CPU 사용량은 기본 표시 약 2.41 논리 코어, 30FPS 약 1.70, NullRHI 약 0.98이었다. 여유 코어가 많아도 다음 물리 단계가 이전 단계에 의존하는 현재 단일 GPU 큐의 계산을 단순히 CPU 스레드 수만큼 가속할 수는 없다.

상세 분리 계측(약 4초 물리 시간)에서 측정한 GPU 이벤트 실행 시간 비중:

| 단계 | 비중 |
|---|---:|
| 입자 접촉 | 31.2% |
| 격자 구성 | 24.0% |
| 벽·날개 투영 | 19.4% |
| 재사용 변위 검사 | 7.1% |
| 격자 초기화 | 6.5% |
| 후보 목록 구성 | 5.3% |
| 재사용 제어 초기화 | 4.1% |
| 나머지 | 약 2.4% |

이는 상세 계측을 켠 실행의 비중이다. 계측 자체가 성능을 크게 바꿨다: 4초 기본 약 0.358배속 → 이벤트 계측 약 0.204배속 → 벽 분리 계측 약 0.194배속. 따라서 위 비중을 기본 실행의 절대 시간으로 환산하거나 측정된 공백을 그대로 제거 가능한 시간으로 해석하면 안 된다.

분리 계측에서는 약 17.77초의 이벤트 실행과 약 2.39초의 명령 사이 간격이 관찰됐다. 간격에는 드라이버·스케줄링·다른 GPU 작업의 영향이 포함될 수 있다. `gpu_batch_span_s`는 수집 단위 내부 구간의 합이며 배치 사이 모든 공백을 포함하지 않는다. profiling=false인 GPU 이벤트 필드 0은 미측정이다.

후보 목록은 99%가량 재사용됐지만 재사용 시 즉시 반환하는 grid/candidate 커널도 계속 제출된다. 이를 줄이는 작업은 후보 유효성 검사를 유지하는 조건으로 연구할 가치가 있다. 커널을 합칠 때 전역 동기화가 필요한 단계를 단순 병합해서는 안 된다.

## 효과가 작거나 역효과였던 변경

- 배치 확대: 12초에서 약 2% 개선. CPU 부담은 감소했으나 주요 가속 수단은 아니었다.
- workgroup 256: 12초 한 차례에서 약 5% 개선, 4초에서는 약 1%. 기본값 채택 전 반복·장시간 검증 필요.
- workgroup 64: 4초 속도 약 0.131배속으로 크게 악화. 적용하지 않음.
- 주기적 readback 생략: 4초 속도 약 0.353배속으로 기본 약 0.358보다 좋아지지 않음. 현재 복사량을 줄이는 것만으로 큰 가속은 기대하기 어려움.

## 검증과 한계

- 코어 회귀 7/7 통과. 새 workgroup/시간 분해 검사 포함.
- 계산 전용 13개 실행의 최종 상태: 입자 수·성분 보존, 유한값, 벽·날개·입자 겹침 기준 통과.
- UE 3개 실행 각각 7개 시점 감사 통과. 최대 겹침/작은 입자 반지름 비율은 기본 2.84%, 30FPS 2.95%, NullRHI 3.73%.
- 순서를 바꾸지 않았어도 GPU atomic 격자 구성과 부동소수점 합산 순서로 반복 실행의 개별 궤적은 달라진다. 비트 단위 동일성이나 실제 분말 정확도를 보장하는 시험이 아니다.
- 측정된 최고 온도 61°C, 최고 전력 134.5W. 기준 초과·GPU 오류 없이 시험 종료. 관측 사이의 순간 피크까지 증명하지는 않는다.
- SM 점유율, 캐시 hit, 레지스터 압박, DRAM 처리량은 이번 측정에 포함되지 않았다. GPU가 바쁘다는 것과 최적 커널이라는 것은 다르다.

## 권장 다음 순서

1. 표시 30FPS를 선택할 수 있는 실행 프리셋 추가와 0.2배속 장시간 재검증. 같은 dt·물성 유지. 화면을 보며 진행할 수 있는 가장 큰 실측 개선 후보.
2. 격자/후보 재사용 시 실행되는 불필요한 GPU 작업 제출 감소. 새 접촉 누락 검사와 전역 동기화 보존.
3. workgroup 256을 반복·장시간 검사하여 장치별 선택 가능성 판단.
4. 입자 접촉과 벽 계산의 메모리/분기/레지스터 사용을 세부 GPU 도구로 조사. 현재 데이터만으로 특정 자원이 포화됐다고 단정하지 않음.
5. CPU 병렬화는 향후 독립 통계·내보내기·복수 조건 실행에 우선 적용. 단일 시뮬레이션의 다음 시간 단계를 여러 스레드에서 동시에 실행하는 방식은 제외.

## 재현

- CMake Release `granular_diagnose` 빌드.
- `python Scripts/diagnose_granular_hardware.py Saved/HardwareDiagnosis/new --steps 32000 --case base,local256,batch128,base_repeat`
- 초기 파일은 `Saved/Rate01Recheck/current12/initial.bin`을 사용하며 SHA가 다르면 거부한다. 파일이 없으면 저장된 BinaryMaterials 레벨의 benchmark로 초기 위치를 다시 내보내고 SHA를 확인해야 한다.
- `Scripts/diagnose_granular_unreal.py`는 고정된 새 결과 폴더가 필요하며 기존 결과 덮어쓰기를 거부한다. 각 실행의 정확한 명령은 `unreal/*/command.json`에 보존했다.
- `Scripts/audit_granular_hardware.py`, `Scripts/audit_binary_material.py`로 계산 전용/UE 결과 감사.
- `Scripts/report_granular_hardware.py`로 측정 JSON과 소스·실행 파일 해시 수집.
